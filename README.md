# CS 255 DriverPass Project Reflection

## Briefly summarize the DriverPass project. Who was the client? What type of system did they want you to design?

The client for the DriverPass project was Liam, the owner of DriverPass, a company that wanted to help students better prepare for their driving tests. 
DriverPass wanted a web-based system where customers could create accounts, purchase training packages, access online practice tests, and schedule in-person driving lessons. 
The system also needed to allow employees and administrators to manage appointments, customer information, and other business operations. 
Throughout the project, I used the client's interview and requirements to create a system design that represented both the business needs and the way users would interact with the system.

## What did you do particularly well?

I think one of the things I did particularly well was translating the client's requirements into UML diagrams that showed how the different parts of the DriverPass system would work together. 
Creating the use case, activity, sequence, and class diagrams helped me look at the same system from several different perspectives. I also did well at keeping the client's original goals in mind instead of adding unnecessary features. 
As I worked through the project, I became more comfortable taking written requirements and turning them into a visual system design that could be understood by both technical and nontechnical audiences.

## If you could choose one part of your work on these documents to revise, what would you pick? How would you improve it?

If I could revise one part of my work, I would spend more time refining my UML diagrams. 
While my diagrams captured the major requirements of the DriverPass system, I think some of the interactions and alternative paths could be represented in more detail. 
For example, I could improve the diagrams by showing additional situations such as invalid login attempts, scheduling conflicts, cancellations, or errors that might occur while a user is completing a task. 
Adding these details would make the design more realistic and give developers a clearer understanding of how the system should respond when something does not go according to the normal process.

## How did you interpret the user's needs and implement them into your system design? Why is it so important to consider the user's needs when designing?

I interpreted the user's needs by reviewing the DriverPass interview and identifying the specific functions that each type of user needed from the system.
For example, customers needed to be able to create accounts, purchase packages, take practice tests, and schedule driving lessons, while employees and administrators 
needed additional tools to manage customers, appointments, and system information. I then represented these requirements throughout the different UML diagrams and system design documents. 
Considering user needs is important because a system can technically function correctly and still fail if it is difficult to use or does not solve the problems the client originally wanted addressed. 
Keeping the user in mind throughout the design process helps ensure that the final system is useful, efficient, and appropriate for the people who will actually use it.

## How do you approach designing software? What techniques or strategies would you use in the future to analyze and design a system?

My approach to designing software is to first understand the problem and the user's requirements before deciding how the system should be built. 
I would start by gathering requirements and identifying the different users, their goals, and the major functions the system needs to provide. 
From there, I would break the system into smaller processes and use tools such as use case, activity, sequence, and class diagrams to visualize how everything should work together. 
I also think it is important to review the design throughout the process rather than assuming the first version is complete. In future projects, 
I would continue using UML diagrams and user requirements while putting even more focus on alternative scenarios, potential errors, security, and feedback from users. 
This project showed me that good software design is not only about creating a system that works, but also about creating one that meets the client's needs and can be clearly understood before development begins.
